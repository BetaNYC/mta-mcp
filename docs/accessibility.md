# Elevators, escalators, and accessibility

This page covers `get_accessibility_outages`, the ADA status every station
carries, and the elevator check `check_route_on_date` can add. It says
what they can tell you, how to read them, and where they fall short. Please
read the gaps section before telling anyone a station is accessible. A wrong
"no outages" can leave a wheelchair user at a station with no way to reach
the platform.

Everything here was checked against the code in `src/`, the saved feeds in
`test/fixtures/` (alerts feed timestamped 2026-09-16, elevator feeds saved
2026-09-17), and the bundled data.ny.gov snapshots in `data/` (pulled
2026-09-22), unless it says otherwise. Where each source
comes from and how they join: [data-sources.md](data-sources.md).

## What it answers

- Which elevators and escalators are out of service right now.
- Which outages MTA has scheduled for the future.
- Which outages, current or scheduled, overlap one date.
- Any of those for one station, by name or by `stop_id`, or for one route.
- What MTA says to do when an elevator is out: its alternate route.
- Whether MTA lists a station as fully, partially, or not accessible, and for
  a partial station, in which direction.

## What it doesn't answer

- **Whether a station is usable today.** MTA's ADA status says a station has
  an accessible path. It doesn't say the path is working, and no listed
  outage doesn't prove it is. See [Gaps](#gaps).
- **Whether an elevator will really be back when MTA says.** The dates are
  MTA's estimates.
- **Anything outside the subway.** No LIRR, Metro-North, or bus data.

For all of these, [MTA's elevator and escalator status page](https://www.mta.info/elevator-escalator-status)
is the official source.

## Where the data comes from

Two MTA feeds, neither needing a key:

| Feed | Returned when | What's in it |
|---|---|---|
| `nyct%2Fnyct_ene.json` | `upcoming: false` (the default), or any `date` | Outages in effect now, plus scheduled ones |
| `nyct%2Fnyct_ene_upcoming.json` | `upcoming: true` | Scheduled outages only |

The two overlap. In the saved feed, the current feed had 126 rows: 79 in effect
now and 47 flagged `isupcomingoutage: "Y"`. The upcoming feed had exactly those
47. So `upcoming: false` reads the current feed and removes the 47, and
`upcoming: true` reads the upcoming feed. Each outage shows up in one answer or
the other, never both.

A `date` query reads only the current feed and keeps all 126 rows, then filters
by date. That's one request instead of two. It relies on the current feed
containing every scheduled outage. We counted that in our saved copy of both
feeds, but MTA doesn't document it, and every date answer's `feed_note` says
so. If MTA ever splits the feeds apart, a date query would miss
scheduled outages. A fresh pull that shows upcoming rows missing from the
current feed is the sign to change this.

Unlike the service alerts, these feeds are plain lists, not GTFS-realtime. Each
row names its station in free text rather than with a `stop_id`. That was the
root of most of the problems below until we added MTA's equipment inventory,
which places each elevator and escalator at a station by ID.

Two more sources ship with the repo as dated snapshots, generated by
`npm run accessibility-data` and never fetched at runtime:

| File | From | What it adds |
|---|---|---|
| `data/station_ada.json` | data.ny.gov [`39hk-dx4f`](https://data.ny.gov/Transportation/MTA-Subway-Stations/39hk-dx4f), MTA Subway Stations | Each station's ADA status, by direction, with MTA's note |
| `data/equipment.json` | data.ny.gov [`94fv-bak7`](https://data.ny.gov/d/94fv-bak7), MTA Subway Elevator and Escalator Asset Inventory | Where each elevator and escalator is, by `stop_id`, and its alternate route |

These come under the OPEN-NY Terms of Use, not MTA's feed terms. See
[data-sources.md](data-sources.md#terms).

## Parameters

| Parameter | Type | Default | Description |
|---|---|---|---|
| `station` | string | none | Station name as free text, matched loosely |
| `stop_id` | string | none | GTFS parent-station id. Rows are placed by equipment ID first, then by the station's name for rows the inventory doesn't cover. See [With a `stop_id`](#with-a-stop_id) |
| `route_id` | string | none | Only rows whose `trainno` includes this route. See [Routes](#routes) |
| `date` | string | none | `YYYY-MM-DD`. Outages in effect now or scheduled whose window overlaps that day in New York time. See [Dates](#dates) |
| `upcoming` | boolean | `false` | `false` for outages in effect now, `true` for scheduled ones |

All filters combine. With none, you get every outage in the feed.

`date` and `upcoming: true` can't be used together. A date query already
covers outages in effect now and scheduled ones, so honoring `upcoming: true`
as well would mean ignoring one of them. `upcoming: false` is the default and
is accepted with `date`.

An unknown `stop_id` and a badly formatted `date` return an error rather than
an empty list.

|---|---|
| `upcoming` | Which of the two feeds this answer came from. `null` for a date query |
| `date` | The date you asked about, or `null` |
| `feed_url` | The exact MTA feed read |
| `query` | The name that was matched. With `stop_id`, this is that station's GTFS name |
| `stop_id` | The `stop_id` you passed, or `null` |
| `route_id` | The `route_id` you passed, or `null` |
| `route_tokens_matched` | The `trainno` values that counted as your route, like `["6X", "6"]`. `null` with no `route_id` |
| `route_note` | A warning when your route matched `S`, since the feed doesn't say which shuttle. Otherwise `null` |
| `station_accessibility` | With `stop_id`, the station's ADA status. See [Station accessibility](#station-accessibility). `null` without one |
| `matched_by` | How rows were matched: by equipment ID first with a `stop_id`, or by name with `station`. `null` if you didn't filter by station |
| `outage_count` | Outages returned in `outages` |
| `rows_in_feed` | Rows read from the feed before any filter. For `upcoming: false`, that's after removing the scheduled rows |
| `feed_note` | Which kind of outage this answer covers |
| `no_match_note` | When a station or route search returns nothing, why that isn't proof of no outage and what to try next. `null` otherwise |
| `rows_without_station` | With a station search, how many returned rows had no `station` name and were kept because they can't be ruled out. `null` without one |
| `date_caveats` | For a date query, the returned rows whose dates couldn't be trusted, with the reason. See [Dates](#dates). `null` with no `date` |
| `outages` | MTA's rows, unchanged, each followed by whichever of our three fields below apply. Rows placed by equipment ID come first, then name matches, best first. The example above shows one of the two |
| `complex_outages` | With `stop_id`, outages at other stations in the same station complex, placed there by equipment ID. `null` if the station isn't in a complex or you didn't pass `stop_id` |
| `other_station_outages` | With `stop_id`, rows that matched the name but belong to another station: the inventory puts them outside this complex, or their `trainno` shares no route with the station. Listed so nothing is hidden. `null` without `stop_id` |
| `inventory_data` | When the equipment inventory snapshot was pulled, its source, and a note that its text can lag |
| `ada_data` | With `stop_id`, the same for the station ADA snapshot. Otherwise `null` |

Each outage row can carry three fields after MTA's. A field with nothing to
say is left out, not set to `null`. `inventory` comes only when you filter by
`station` or `stop_id`, which keeps the unfiltered and route-only answers
small: on the saved feed, the unfiltered answer is about 29,000 characters.

| Field | Meaning |
|---|---|
| `matched_by` | `"equipment id"`, `"name"`, or `"partial name"`: how this row was tied to your station. Absent when you didn't filter by station, or for a row with no station name |
| `match_note` | Why a row is here when the evidence is mixed: the inventory places it at another station in the complex, or a closer name belongs to another station. Otherwise absent |
| `inventory` | From MTA's equipment inventory: `stop_ids` (where the equipment is), `ada_compliant`, `redundant_elevator`, and `alternative_route`. Absent without a station filter, or if the code isn't in the inventory. See [Alternate routes](#alternate-routes) |

Every answer also carries the provenance fields described in
[docs/tools.md](tools.md#provenance-on-every-answer). `feed_timestamp` is
always `null` here, because these feeds don't include one.

### MTA's fields, row by row

The tool passes MTA's rows through unchanged, with MTA's field names. MTA's
[developer page for these feeds](https://www.mta.info/developers/display-elevators-NYCT)
defines only one of them, `ADA`. The rest are described from what we see in the
data, and marked that way.

| Field | Meaning | Source |
|---|---|---|
| `ADA` | `"Y"` if the elevator is part of the station's accessible path. In MTA's words, it shows "if an elevator is part of an accessible pathway." An outage with `"Y"` can make the station unusable for someone who can't use stairs | MTA |
| `station` | Station name, in MTA's spelling for this feed, which doesn't always match the station list | Observed |
| `trainno` | Routes at the station, slash-separated, like `"B/D"` or `"A/C/E/L"`. Sometimes includes other services, like `LIRR`. Never an express or shuttle id like `6X` or `GS` | Observed |
| `equipment` | MTA's id for the elevator or escalator, like `"EL433"` | Observed |
| `equipmenttype` | `"EL"` for elevator, `"ES"` for escalator | Observed |
| `serving` | Which parts of the station it connects, like `"mezzanine to Manhattan-bound platform"` or a street corner. This is the most useful field for a rider | Observed |
| `outagedate` | When the outage started or starts, as `MM/DD/YYYY hh:mm:ss AM`. The time zone isn't stated. The tool passes it through unchanged, and reads it as New York time for `date` | Observed |
| `estimatedreturntoservice` | MTA's estimate for the fix, same format. An estimate, not a promise | Observed |
| `reason` | Free text. Seen values: `Maintenance`, `Capital Replacement`, `Repair`, `Inspection`, `Planned Work`, `Con Edison Power Issue`, `Station is Under Rehabilitation` | Observed |
| `isupcomingoutage` | `"Y"` for a scheduled outage, `"N"` for one in effect | Observed |
| `ismaintenanceoutage` | `"Y"` or `"N"`. Every row in our sample was `"N"`, including rows with `reason: "Maintenance"`, so we don't rely on it | Observed |
| `borough` | Empty in every row we've seen | Observed |

In the saved feed: 81 elevator rows and 45 escalator rows, and 80 rows with
`ADA: "Y"` against 46 with `"N"`.

## How station matching works

With a `stop_id`, the tool first looks up each row's `equipment` in MTA's
equipment inventory, which gives the `stop_id` it sits at. That's the ID
match, and it wins. Name matching is the fallback, for rows the inventory
doesn't place, and the evidence when the two point at different stations in
one complex. With `station` as free text, rows are matched by name only.

### Matching by name

Both the query and each row's `station` are lowercased and split into words,
with punctuation removed. Three more rules even out the ways MTA spells
stations in this feed:

- A number glued to letters is split: `42St` becomes `42 st`.
- `pk` becomes `park`. MTA's own station list uses both spellings (`42 St-Bryant
  Pk` and 13 stations with `Park`), so this is applied on both sides.
- `pl` becomes `place`, for the same reason: the station list has both
  `Park Pl` (S03) and `Park Place` (228), plus `Astor Pl`.
- `th`, `nd`, and `rd` right after a number are dropped, so a typed
  `"34th St"` or `"42nd St"` matches. Neither the station list nor the saved
  feed writes an ordinal after a number. `st` stays, since after a number it
  almost always means Street.

So `"42St/Port Authority-Bus Terminal"` becomes
`42 st port authority bus terminal`, the same words as the GTFS name
`42 St-Port Authority Bus Terminal`. Then each row gets a score:

| Score | When |
|---|---|
| 100 | Same words, same order |
| 80 | The row's name starts with your words |
| 60 | Your words appear together somewhere in the row's name |
| 40 | All your words appear, in any order |
| 0 | Otherwise. The row is left out |

Rows scoring above 0 are returned, highest first. These rules apply only to
this tool. `resolve_station` matches GTFS names the way it always has.

In the saved feed there are 58 distinct station names. 55 match a GTFS name
character for character, and 56 word for word under the old matching. With
these rules, all 58 match some GTFS name, though not always the station you
asked about by `stop_id`. See below.

### With a `stop_id`

Each row lands in one of four places:

1. **The inventory places it at your station.** It goes in `outages` with
   `matched_by: "equipment id"`.
2. **The inventory places it at another station in the same complex.** If the
   row's name also fits your station, it stays in `outages`, matched by name,
   with a `match_note` saying where the inventory puts it. Several stations in
   a complex often share a name (Times Sq-42 St is four), and the equipment
   may serve more than the one station it's coded to, so we keep it. If the
   name doesn't fit, it goes to `complex_outages`. Asking about Times Sq-42 St
   (`127`) lists the Port Authority elevator EL290X there.
3. **The inventory places it somewhere else.** If the name matched, it goes to
   `other_station_outages` with a note. `Union St` (`R32`) used to pick up the
   14 St-Union Sq rows on the R; now they're set aside.
4. **The inventory doesn't have it.** The name rules decide. A row whose
   `trainno` shares no route with the station goes to `other_station_outages`.
   A row with no `station` at all stays, since we can't rule it out, and is
   counted in `rows_without_station`.

For rows the inventory doesn't cover, the tool also matches a row whose name
is a shorter form of the station's GTFS name, like `Court Sq` for
`Court Sq-23 St` (`F09`) or `Cortlandt St` for `WTC Cortlandt` (`138`). Every
word of the row's name, other than street types like `St` and `Av`, has to be
in the GTFS name, one of them has to be something other than a number, and the
row's `trainno` has to share a route with the station. That's
`matched_by: "partial name"`. If another station on that route has a closer
name, the row is still returned, with a `match_note` naming the closer
station. `Cortlandt St` on the 1 fits both `WTC Cortlandt` and
`Van Cortlandt Park-242 St`. It used to go only to the closer one, which could
hide an outage from a station it plausibly belongs to.

In the saved feeds every row's equipment is in the inventory, so today this
fallback only runs when MTA lists equipment the snapshot doesn't have. See
[data-sources.md](data-sources.md#how-they-join) for how the ID join changed
the answers: 13 name-only pairings that were wrong now go to
`other_station_outages`, and 3 rows name matching missed are now found.

A `station` search doesn't use the inventory to filter, since it doesn't know
which station you mean. Each row's `inventory.stop_ids` still tells you where
MTA says the equipment is, which is the quickest way to sort out a name like
`125 St`.

## Station accessibility

Every station in `resolve_station`, `check_route_on_date`, and
`get_accessibility_outages` with a `stop_id` carries MTA's ADA status:

```json
{ "status": "partially_accessible", "mta_notes": "Uptown local only", "accessible_direction": "Uptown" }
```

| `status` | MTA's `ada` | Meaning |
|---|---|---|
| `fully_accessible` | 1 | MTA lists an accessible path in both directions |
| `partially_accessible` | 2 | Accessible in one direction only. Lead with `mta_notes`. `accessible_direction` is MTA's label for that direction, like `"Manhattan"` or `"Uptown"` |
| `not_accessible` | 0 | MTA lists no accessible path |
| `unknown` | none | The station isn't in the snapshot. It's never reported as not accessible |

`mta_notes` is MTA's `ada_notes`, word for word, and it's what to say to a
rider. It can be narrower than the direction: 86 St on the Lexington Avenue
line (`626`) is accessible Uptown, and MTA's note says "Uptown local only."
In the 2026-09-22 snapshot there are 9 partially accessible stations, and
every one is accessible in exactly one direction.

`accessible_direction` is MTA's rider label for the accessible side, taken
from `north_direction_label` or `south_direction_label`. We don't say
"northbound" or "southbound": GTFS directions are nominal, so the
Manhattan-bound side of Court Sq-23 St (`F09`) is its "southbound" side. The
field is built from MTA's `ada_northbound` and `ada_southbound` flags, so if
MTA ever marks a station partial some other way, it will be `null` and the
note is all we have.

The status is per station, not per complex. At 14 St-Union Sq, the L and
N/Q/R/W stations are accessible and the 4/5/6 station (`635`) isn't.

This is MTA's designation, from a dated snapshot. It doesn't change when an
elevator breaks, and MTA posts it as needed, so a station that just
became accessible may still read `not_accessible`. Each answer's `ada_data`
gives the pull date.

## Alternate routes

MTA's equipment inventory has an `alternative_route` for 427 of its 481
elevators, and for none of the escalators. It's MTA's own text, telling a
rider how to get around that elevator when it's out. The tool returns it in
each outage row's `inventory`, unchanged. `redundant_elevator` is `"+"` when
MTA says another elevator provides the same service and `"-"` when none does.

Two warnings, both from MTA:

- It's maintained by hand, and MTA's overview of the dataset says updates to
  hand-populated features "may be lagged."
- Some of it describes one particular outage. EL433's reads "All elevators at
  this station are out of service for replacement," which was true for one
  project.

So quote it as MTA's, with the snapshot date from `inventory_data`, and
confirm it on [mta.info](https://www.mta.info/elevator-escalator-status)
before putting it in front of riders. Don't rewrite it into directions of
your own.

## Elevators in `check_route_on_date`

`check_route_on_date` always returns the station's ADA status in
`station.accessibility`. That's bundled, so it costs nothing.

Pass `include_accessibility: true` with a station and it also returns
`accessibility_outages`: elevator and escalator outages at that station on
that date, placed the same way as above, with MTA's alternate route on each.
That's one more request, to the current elevator feed, and only when you ask.
Without a station it's an error, since the outages are per station. If the
station name is ambiguous, you get the candidates and no elevator request is
made.

| Field | Meaning |
|---|---|
| `feed_url`, `fetched_at` | The elevator feed read, and when |
| `outage_count` | Outages at this station that day |
| `outages` | A short form of each row: `equipment`, `equipmenttype`, `serving`, `ADA`, `outagedate`, `estimatedreturntoservice`, `reason`, `matched_by`, `match_note`, `alternative_route`, and `date_caveat` |
| `complex_outages` | The same, for other stations in the complex. `null` if the station isn't in one |
| `other_station_outage_count` | Rows that matched the name but belong to another station. `get_accessibility_outages` lists them |
| `note` | What this covers, what an empty list does and doesn't mean, and where to confirm |

For the full detail, including `date_caveats` and rows set aside, call
`get_accessibility_outages` with the same `stop_id` and `date`.

## Routes

`route_id` keeps rows whose `trainno` includes the route, as a whole value
between slashes, commas, or spaces, so `L` doesn't match `LIRR`. The feed never uses GTFS's
express or shuttle ids, so we map them:

| `route_id` | Matches `trainno` | Basis |
|---|---|---|
| `6X`, `7X`, `FX` | `6`, `7`, `F` | The express stops at its local's stations. None of the 126 rows says `6X`, `7X`, or `FX` |
| `GS` | `S` | Observed. All 6 rows with `S` are at Times Sq-42 St, Grand Central-42 St, and 42St/Port Authority, the 42 St Shuttle and its complex |
| `FS`, `H` | `S` | Not observed. No row is at a Franklin Av or Rockaway Park Shuttle station. We map them so an outage there isn't missed |

The route id itself always matches too, in case MTA starts using it. Because
`S` doesn't say which shuttle, any route that matches `S` gets a `route_note`,
and `FS` or `H` will return the 42 St rows as well. Check each row's `station`.

## Dates

`outagedate` and `estimatedreturntoservice` look like
`09/16/2026 11:55:00 PM`. All 252 values in the saved current feed have that
shape. MTA doesn't say what time zone they're in. We read them as New York
time, like every other date in this server.

An outage counts for a date if its window, from `outagedate` up to
`estimatedreturntoservice`, overlaps that day in New York time. Returning at
exactly midnight doesn't touch the next day.

Rows are kept, not dropped, when the dates can't be trusted. Each one is listed
in `date_caveats` with one of these:

| `caveat` | When |
|---|---|
| `unparseable_date` | A date is missing or isn't in the shape above |
| `inconsistent_dates` | The return estimate is before the start |
| `estimate_passed` | The estimate had already passed when the feed was fetched, and MTA still listed the outage. We treat it as ongoing with no end. Listed only for dates the original window didn't cover |

The reasoning behind `estimate_passed`: an elevator that was due back last
week and is still in the feed is still out. We don't know how often MTA's feed
lags its estimates live. In the saved feed, pulled September 17, 50 of the 79
in-effect rows were due back on September 17 or 18, so a live answer can carry
several of these.

## Gaps

These are real problems in the current tool. Each one can produce a wrong
answer that looks right.

### 1. An empty answer doesn't mean the station is usable

A station with no listed outage may still be unusable. The feed can lag, an
outage MTA hasn't entered won't show, and a station MTA lists as
`not_accessible` has no accessible path to break. An empty answer's
`no_match_note` says so, and `check_route_on_date`'s elevator `note` says so.
Pass it on.

### 2. The snapshots can be out of date

The ADA status and the alternate routes come from snapshots pulled on the date
in `ada_data` and `inventory_data`. MTA updates station status as needed and
says its hand-kept inventory fields may lag. A newly opened elevator, a
station that just became accessible, or a rewritten alternate route won't
show until someone runs `npm run accessibility-data`.

### 3. The sources don't always agree

- Four stations MTA lists as not accessible have an ADA-compliant elevator
  coded to them in the inventory: 149 St-Hostos, 14 St-Union Sq (`635`),
  42 St-Bryant Pk, and Fresh Pond Rd. A scheduled-outage query on `635`, the
  4/5/6 station at Union Sq, lists EL217, an ADA elevator from the street to
  the mezzanine for the L and N/Q/R/W, at a station MTA marks not accessible.
  We report the station's status as MTA publishes it and never infer
  accessibility from elevators. When one of these stations has no outage, the
  answer names its ADA elevators instead of saying there may be none.
- 13 stations MTA lists as accessible have no ADA-compliant elevator in the
  inventory, including six on the Staten Island Railway.
- 23 pieces of equipment have no station in the inventory. Most are in yards
  and shops, but two are street elevators at New Dorp on the Staten Island
  Railway. An outage on one of them is matched by name only.
- Some outage rows name one station while the inventory codes the equipment to
  another in the same complex. We list those at both, with a `match_note`.

### 4. Some stations may still be missed by name

Rows the inventory can't place are matched by name, and a `station` search is
always by name. We fixed the spellings we found (see
[Matching by name](#matching-by-name)), but others may appear as the feed
changes, and a `station` search by the full GTFS name still misses a row whose
name is shorter, like `"WTC Cortlandt"`.

Every empty station or route search comes with a `no_match_note`. When it
appears, search again with a short, distinctive part of the name, or pass
`stop_id`, and check what comes back. Never report "no outages" from one
search.

### 5. Same name, different station, by name alone

A search by `station` doesn't know which routes you mean. `"125 St"` can
return an outage at any of four stations. Use `stop_id`, or check each row's
`inventory.stop_ids` and `trainno`.

### 6. The dates are MTA's estimates

A date query tells you what MTA's feed says for that day. An outage that
starts later than MTA planned, or runs long without the feed catching up,
won't show. For a date more than a few days out, check again closer to it.

## Checking accessible directions for an event

1. `check_route_on_date` for each route you're recommending, with the
   station's `stop_id`, the date, and `include_accessibility: true`.
2. Read `station.accessibility`. If it's `partially_accessible`, say which
   direction, in MTA's words from `mta_notes`. If it's `not_accessible`,
   don't describe the station as accessible, whatever the outages say.
3. For each outage, note whether `ADA` is `"Y"`, what it's `serving`, and the
   `alternative_route`. Read any `match_note` and `date_caveat`, and look at
   `complex_outages`.
4. For the full detail, run `get_accessibility_outages` with the same
   `stop_id` and `date`, and check `other_station_outages`.
5. Confirm on [mta.info](https://www.mta.info/elevator-escalator-status).
6. In the copy, name the station and entrance, say when you checked, and tell
   people to confirm before they travel. Quote an alternate route as MTA's.

## Accessibility of this project itself

MTA's alerts page shows route names as images, so a screen reader or a
copy-paste loses which train an alert is about. This server returns routes as
text (`"6"`, `"A"`), and quotes MTA's `header_text`, which writes routes as
`[6]`. Answers work with a screen reader and paste cleanly into email.
