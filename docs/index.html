mta-mcp

Before every BetaNYC event, we check the trains and elevators on the way there, so nobody who uses a wheelchair gets sent to a station whose elevators are out. We want to know whether the train we're telling people to take is running that day, at that station. Checking by hand is slow and easy to get wrong, so we built an MCP server that lets an AI assistant like Claude do it.

You ask something like "Is the 6 train running to 68 St–Hunter College on Saturday, October 3?" It reads MTA's service alerts and elevator outage feeds and tells you what affects that station on that date. It's an unofficial tool. BetaNYC is not the MTA.

When to use something else

If your question is "is the L running right now," use mta.info or any transit app. They're free and official, and they show what's happening now.

This server is for planning ahead: a future date, a specific station, and an answer you can put in the email to everyone coming. For live arrivals inside an AI assistant, try one of the other NYC subway servers further down.

Each example below is labeled. Verified 2026-09-21 means we ran that call live that day. Saved feed means we ran it against copies of MTA's feeds saved in the repo, dated on the panel. Illustrative shows a call Claude might make, not one we ran.

When an alert means more trains

An alert can mention your station because service there got better.

"Is the 4 train disrupted at 68 St–Hunter College on Sat Sep 26?" Verified 2026-09-21
By hand
  1. Open mta.info/alerts. Filter to the 4, set the date to 09/26.
  2. Read the results. Route names render as images, so a copy-paste or a screen reader loses which train each alert is about.
  3. Find "4 runs local between 125 St and Grand Central." Your station is on that stretch, so it is mentioned.
  4. Decide what "mentioned" means. Is local service better or worse for you?
  5. Notice a second alert with no station list at all, and decide whether it matters.
Steps 4 and 5 are judgment calls, and getting step 4 wrong gives you a false alarm.

The express-to-local alert tags 68 St and doesn't count as a disruption, because running local means more trains stop there. The second alert names no stations, so the tool won't say your station is clear. It reports a disruption and names the alert that caused it.

Counting any mention as a disruption would flag 68 St here, because the alert that names it adds service. This server reads MTA's alert_type to tell the two apart.

What Claude can tell you from it
MTA lists this station as fully accessible. On this saved feed, five of its elevators are out, three of them with an estimated return of January 31, 2027, so the ADA status alone can't tell you the station is usable. Each outage carries MTA's own alternate route. The one above sends riders to the 6 train between 125 St and Hunts Point Av, and the saved alerts feed shows no 6 train on that stretch that weekend. The return dates are MTA's estimates. Check MTA's elevator and escalator status page before you send anyone.

Once it's installed, you ask Claude a question in plain English, and Claude picks a tool and fills in the arguments. It works best when the question names a train, a station, and a date.

What Claude can tell you from it
The one alert on the 6 that weekend is in the Bronx, between Hunts Point Av and 125 St, and MTA didn't tag 68 St, so disrupted is false for this station. Guests coming from the Bronx on the 6 would still hit the gap, and MTA's alert text says free shuttle buses cover it. A flyer should still tell people to check mta.info before traveling.

Running it

1. Clone and build

You need Node 18 or newer, and no API key.

git clone https://github.com/BetaNYC/mta-mcp.git
cd mta-mcp
npm install    # also builds

2. Point your AI app at the build

For Claude Code, in a project's .mcp.json:

{
  "mcpServers": {
    "mta-mcp": {
      "command": "node",
      "args": ["${HOME}/Code/mta-mcp/dist/index.js"]
    }
  }
}

For Claude Desktop, in claude_desktop_config.json. Claude Desktop doesn't expand ${HOME}, so use the full path to your copy:

{
  "mcpServers": {
    "mta-mcp": {
      "command": "node",
      "args": ["/absolute/path/to/mta-mcp/dist/index.js"]
    }
  }
}

3. Ask a question

Restart the app and ask something from Try asking, like "Check the 6 train and the elevators at 68 St–Hunter College for October 3."

Using Claude Code and want to use fewer tokens per conversation? The same tools also come as a skill, with no MCP server to run. See skills/README.md.

What it can't do yet

Not thisWhy
"When is the next 6 train?" No arrivals or trip updates, for the subway or buses. The subway arrival feeds are protobuf-only, and Bus Time needs an API key. The servers below do live subway arrivals.
"Are Times Sq and Port Authority connected?" Stations linked only by transfer, under different names, are not modeled. 60 such pairs exist. Asking about one name will not surface alerts filed against the other.
"Can I get step-free to the platform today?" Only in part. You get the station's ADA status and any elevator outages MTA has listed, with its alternate route. The ADA status is a dated snapshot and the outage feed can lag, so an empty answer doesn't mean the station is usable. Check MTA's elevator and escalator status page.
"Is my station definitely fine?" MTA tags stations only when it considers the change significant. Every response carries station_level_detail, which is true only when every matching alert named its stations. When it's false, a clean answer for your station isn't a guarantee.

What we haven't settled

  • We've only inspected the subway alerts feed. Bus, Long Island Rail Road, and Metro-North alerts are untested. MTA's docs say all four feeds append a status rank to every alert id, and we found one on 1 of 150 subway entities. We don't know if that's a partial rollout or a documentation error, so we use a different field.
  • The effect classification covers the 11 alert_type values we saw in a live pull on 2026-09-16. MTA can send others. An unrecognized value counts as a disruption until someone adds it to the map.
  • MTA publishes no rate limit or refresh cadence. We cache answers for 60 seconds and wait at least a second between requests, which is a cautious guess. The server never polls in the background, and the test suite never calls MTA.
  • We've tested it against a handful of real dates and stations.

Want bus or LIRR alerts, or found something wrong? Open an issue.

Why you have to build it yourself

Our other seven MCP servers install from npm. This one runs from a local build because of MTA's data feed terms, which say users of an app have to get MTA's data from a non-MTA server. A published package would have every user's machine fetch straight from api-endpoint.mta.info, with no server of ours in between. MTA's wording and our reasoning are in docs/terms-compliance.md.
